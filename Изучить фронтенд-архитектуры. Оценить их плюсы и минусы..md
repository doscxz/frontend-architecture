# Фронтенд-архитектуры: плюсы и минусы

Архитектура фронтенд-проекта определяет, **как код разделён на части, где что хранится, как называются папки и кто от кого может зависеть**. Ниже архитектуры идут от простых к сложным. Для каждой: суть, структура папок, правила, плюсы, минусы и когда использовать.

| #   | Архитектура           | Суть в одной фразе                                                        |
| --- | --------------------- | ------------------------------------------------------------------------- |
| 1   | MVC                   | Данные, отображение и обработка ввода разделены на три роли               |
| 2   | MVP                   | View пассивна, вся логика отображения в Presenter                         |
| 3   | MVVM                  | View автоматически связана с состоянием ViewModel через data binding      |
| 4   | По типам файлов       | Папки по техническому типу: `components/`, `hooks/`, `utils/`             |
| 5   | Feature-based         | Папки по фичам, каждая фича - мини-приложение                             |
| 6   | Feature-Sliced Design | Стандартизированные слои → слайсы → сегменты со строгим правилом импортов |
| 7   | Atomic Design         | UI-компоненты по уровням: атомы → молекулы → организмы                    |
| 8   | Clean / Hexagonal     | Бизнес-логика в центре и не зависит от фреймворка                         |
| 9   | Монорепозиторий       | Несколько приложений и общие пакеты в одном репозитории                   |
| 10  | Микрофронтенды        | Независимые приложения разных команд, собранные в одно                    |

## 1. MVC (Model-View-Controller)

Предложен Trygve Reenskaug в 1979 году для Smalltalk-80. Позже стал основой серверных веб-фреймворков (Rails, Django, ASP.NET MVC, Laravel) и первых фронтенд-фреймворков (Backbone.js, Ember.js, ранний AngularJS).

- **Model** - данные и бизнес-логика. Ничего не знает о View, уведомляет подписчиков об изменениях (паттерн Observer).
- **View** - отображает данные Model, подписана на её изменения.
- **Controller** - принимает пользовательский ввод, изменяет Model и/или выбирает, какую View показать.

```text
Пользователь → View → Controller → Model
                ↑                    │
                └──── уведомление ───┘
```

**Структура папок:**

```text
src/
├── models/          - данные и бизнес-правила (+ запросы к API)
│   ├── User.ts
│   └── Cart.ts
├── views/           - шаблоны и компоненты отображения
│   ├── UserView.ts
│   └── CartView.ts
├── controllers/     - обработка ввода, связывание моделей и видов
│   ├── UserController.ts
│   └── CartController.ts
├── router.ts        - выбор контроллера по URL
└── main.ts
```

**Правила и нейминг:** суффикс роли в названии файла (`CartController`, `CartView`), один контроллер на экран или ресурс. Model не импортирует View и Controller. View читает Model, но не меняет её напрямую, а передаёт события в Controller.

**Главная идея, пережившая сам MVC** - _Separated Presentation_ (Fowler): доменные объекты полностью самодостаточны и работают без ссылок на UI. Второе наследие - _Observer Synchronization_: View не обновляют вручную, а подписывают на изменения модели. Обе идеи есть в любом современном фреймворке.

**Плюсы:** простая и всем известная модель разделения ответственности. Model переиспользуется и тестируется отдельно от UI. Основа для понимания всех остальных архитектур.

**Минусы:** во фронтенде границы View и Controller размываются (обработчики событий живут прямо в компоненте). Controller разрастается («Massive View Controller»). При многих моделях и видах двусторонние связи Model↔View дают каскадные и непредсказуемые обновления: именно эту проблему Facebook решал однонаправленным потоком данных (Flux). Раскладка папок по ролям (`models/`, `views/`, `controllers/`) страдает теми же недостатками, что и структура по типам файлов (см. п. 4).

**Когда использовать:** серверный рендеринг (Rails, Django, Laravel + шаблоны), небольшие приложения на vanilla JS, легаси на Backbone. Внутри модуля - как базовая идея «данные отдельно, отображение отдельно».

## 2. MVP (Model-View-Presenter)

Развитие MVC (Taligent, 1990-е). View становится **пассивной**: только отображает данные и передаёт все события Presenter'у.

- **View** - реализует интерфейс (контракт), не содержит логики, не обращается к Model.
- **Presenter** - вся логика отображения: получает события от View, обращается к Model, вызывает методы View через интерфейс.
- **Model** - как в MVC.

Ключевое отличие от MVC: **Model и View никогда не общаются напрямую**, только через Presenter.

```text
View (интерфейс) ⇄ Presenter ⇄ Model
```

**Структура папок:**

```text
src/
├── models/
│   └── UserModel.ts
├── views/
│   ├── IUserView.ts         - контракт: showUser(), showError(), showLoading()
│   └── UserView.tsx         - реализация контракта (компонент)
└── presenters/
    ├── UserPresenter.ts     - логика: load() → model → view.showUser()
    └── UserPresenter.test.ts
```

**Правила и нейминг:** на каждый экран - пара `IXxxView` (контракт) + `XxxPresenter`. View не импортирует Model. Presenter работает с View только через интерфейс.

**Два варианта MVP (Fowler):**

- **Passive View** - View вообще без логики, Presenter сам выставляет каждое поле. Максимальная тестируемость, но больше кода.
- **Supervising Controller** - простую синхронизацию делает data binding, Presenter берёт только сложную логику. Меньше кода, но часть поведения уходит в декларативный binding и хуже покрывается тестами.

**MVP в React:** близкий по духу приём - **Container/Presentational components**: «глупый» компонент получает всё через props, контейнер управляет данными. С появлением хуков контейнер заменяется кастомным хуком (`useDogImages()` → `<DogImages dogs={...} />`), отдельный компонент-обёртка больше не нужен (patterns.dev).

**Плюсы:** максимальная тестируемость - Presenter проверяется как обычный класс, без DOM и рендеринга, с моком View. Чёткий контракт между UI и логикой, View можно заменить (web, mobile, тестовая).

**Минусы:** много boilerplate (интерфейс и Presenter на каждый экран). Presenter может стать таким же «толстым», как Controller в MVC. Императивные вызовы `view.showX()` плохо сочетаются с декларативными React и Vue.

**Когда использовать:** виджетный или императивный UI (vanilla JS, legacy, Android исторически), экраны со сложной логикой отображения и жёсткими требованиями к unit-тестам.

## 3. MVVM (Model-View-ViewModel)

Представлен Microsoft (John Gossman) в 2005 году для WPF/Silverlight и основан на Presentation Model Martin Fowler. Во фронтенде это основа **Knockout.js**, **Angular** и **Vue**.

- **Model** - данные и бизнес-логика, сервисы доступа к API.
- **ViewModel** - состояние экрана и команды в виде **наблюдаемых (реактивных) свойств**. Готовит данные для отображения и **не имеет ссылки на View**.
- **View** - декларативный шаблон, **связанный (data binding)** со свойствами ViewModel. Связь бывает односторонней или двусторонней (two-way binding).

```text
View ⇄ (data binding) ⇄ ViewModel → Model
```

**Как роли ложатся на фреймворки:**

| Роль      | Angular                                                          | Vue 3                                                        | React (по аналогии)            |
| --------- | ---------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------ |
| View      | Шаблон `user-profile.html`                                       | `<template>` в `.vue`                                        | JSX компонента                 |
| ViewModel | Класс компонента `user-profile.ts` (signals, `computed`, методы) | `<script setup>` / composable `useXxx()` (`ref`, `computed`) | Кастомный хук `useXxx()`       |
| Model     | Сервисы (`user-api.ts`), модели/интерфейсы                       | Модули API, Pinia-сторы                                      | API-слой, TanStack Query, стор |
| Binding   | `[prop]`, `(event)`, `[(ngModel)]`                               | `:prop`, `@event`, `v-model`                                 | Односторонний: props + колбэки |

**Структура папок (Vue):**

```text
src/
├── models/                   - Model: типы и доступ к данным
│   ├── user.types.ts
│   └── user.api.ts
├── viewmodels/               - ViewModel: composables с реактивным состоянием
│   └── useUserProfile.ts     - ref, computed, методы save(), validate()
└── views/                    - View: шаблоны, только binding
    └── UserProfile.vue
```

**Структура папок (Angular)** - MVVM встроен в сам фреймворк:

```text
src/
├── main.ts
└── movie-reel/                  - папки по фичам, а не components/, services/
    └── user-profile/
        ├── user-profile.html    - View
        ├── user-profile.ts      - ViewModel (класс UserProfile)
        ├── user-profile.css     - стили
        ├── user-profile.spec.ts - тест рядом с кодом
        └── user-api.ts          - Model (доступ к данным)
```

**Правила и нейминг:**

- В шаблоне нет сложной логики, только binding. Сложные выражения выносятся в `computed` класса. ViewModel не обращается к DOM. Доступ к данным - только через Model/сервисы.

- **Angular (актуальный Style Guide, v20+):** суффиксы `.component`/`.service` в именах файлов **больше не рекомендуются** - `user-profile.ts` для класса `UserProfile`. Слова разделяются дефисом, тесты - `.spec.ts` рядом с кодом. Папки - **по фичам**, а не `components/`, `directives/`, `services/`. Избегайте файлов `helpers.ts`, `utils.ts`, `common.ts`. Члены класса, используемые только шаблоном, помечаются `protected`, DI - через `inject()`. Старый стиль `user-profile.component.ts` встречается в легаси и в проектах до v20.

- **Vue:** composables называются `useXxx`.

**Плюсы:** декларативная синхронизация UI и состояния без ручных вызовов обновления DOM. ViewModel не знает о View, поэтому тестируется без рендеринга. Меньше кода для форм. Хорошо поддерживается фреймворками «из коробки».

**Минусы:** обильный двусторонний binding создаёт скрытый граф зависимостей, и трудно понять, что вызвало обновление. Сложно отлаживать каскады реактивных изменений. ViewModel легко раздувается до «God ViewModel». Сам автор паттерна John Gossman признавал: для простого UI MVVM - overkill, в больших приложениях трудно заранее обобщить ViewModel, а массовый data binding бьёт по производительности.

**Когда использовать:** Vue и Angular (паттерн встроен), формоёмкий UI (админки, CRM, конфигураторы) с множеством связанных полей, приложения, где важна отделимость логики экрана от шаблона.

> **Роли MVC/MVP/MVVM в современных проектах.** Раскладка по ролям (`models/`, `views/`, `controllers/`/`viewmodels/`) хорошо работает в небольших приложениях, но в большом проекте код одной фичи оказывается разбросан по нескольким папкам. Поэтому в современных проектах папки делят **по фичам** (п. 5-6), а роли MVC/MVVM живут **внутри** каждой фичи:

```text
features/add-to-cart/
├── ui/AddToCartButton.tsx     ← View
├── model/useAddToCart.ts      ← ViewModel / Presenter (хук или composable)
└── api/addToCart.ts           ← Model (доступ к данным)
```

### Слоистая архитектура React-приложения (Presentation-Domain-Data)

Вариант тех же идей для React, описанный на сайте Martin Fowler (Juntao Qiu, _Modularizing React Applications_). React - это только View, поэтому остальное приложение делится на слои:

```text
src/
├── components/        View: JSX без логики
├── hooks/             Presentation: состояние экрана, связывание с данными (useXxx)
├── models/            Domain: доменные объекты, расчёты, маппинг, стратегии
└── api/               Data: сетевой клиент, запросы
```

- **Проблема-триггер:** логика «размазана» по компонентам. Новая страна или валюта требует правок в десятке мест (_shotgun surgery_).

- **Решение:** вынести ветвления в доменную модель и заменить `switch`/таблицы на полиморфизм (паттерн Strategy: `PaymentStrategy` с реализациями под каждую страну).

- **Headless Component** - развитие идеи: вся логика и доступность (a11y) в хуке, разметка у потребителя. Так устроены TanStack Table, Downshift, Headless UI, React Aria, Radix. Хорошо подходит для дизайн-систем, где поведение одно, а визуальные варианты разные.

## 4. Структура по типам файлов (Group by type)

Самый простой подход: код группируется по **техническому типу**. Его генерирует большинство стартовых шаблонов (Create React App, Vite).

**Структура папок:**

```text
src/
├── components/   - все компоненты проекта
├── hooks/        - все хуки
├── services/     - все запросы к API
├── store/        - весь стейт
├── utils/        - все утилиты
├── types/        - все типы
├── pages/        - страницы
└── App.tsx
```

**Правила:** фактически отсутствуют. Любой файл может импортировать любой другой.

**Улучшенный вариант - по типам + colocation** (Josh Comeau): верхний уровень остаётся техническим, но всё, что относится к одному компоненту, лежит в его папке:

```text
src/
├── components/
│   └── Widget/
│       ├── Widget.tsx
│       ├── WidgetChild.tsx          - дочерний компонент, нужный только Widget
│       ├── Widget.helpers.ts        - хелперы только этого компонента
│       ├── Widget.constants.ts
│       ├── Widget.types.ts
│       ├── use-widget-state.ts      - хук только этого компонента
│       └── index.ts                 - export { default } from './Widget'
├── hooks/                           - только хуки, нужные 2+ компонентам
├── helpers/                         - доменные хелперы (auth.helpers.ts)
├── utils/                           - общие утилиты (утилиты для любого проекта)
└── constants.ts
```

**Рекомендации React-команды (legacy React docs, FAQ «File Structure»):**

- Не тратьте на выбор структуры больше пяти минут. Если не знаете, с чего начать, держите всё в одной папке и разделите, когда станет понятно, какие файлы меняются вместе.
- Не больше 3-4 уровней вложенности: глубокая вложенность усложняет относительные импорты и переносы.
- Структуры по типам и по фичам на практике смешиваются, так что «правильный» выбор на старте не критичен.

**Плюсы:** нулевой порог входа, не нужно ничего решать. Для проекта на 10-20 компонентов это самый быстрый вариант.

**Минусы:** код одной фичи размазан по 5-6 папкам: чтобы изменить «корзину», надо пройти по `components/`, `hooks/`, `services/`, `store/`. Папки разрастаются до сотен файлов, границ между фичами нет, удалить фичу целиком невозможно, связанность растёт бесконтрольно.

**Когда использовать:** прототипы, pet-проекты, лендинги, маленькие приложения одного разработчика без планов на рост.

## 5. Feature-based / модульная архитектура (Bulletproof React)

Код группируется по **фичам (бизнес-модулям)**. Каждая фича - мини-приложение со своими компонентами, API, стейтом и типами. Эталонная и самая цитируемая реализация - [Bulletproof React](https://github.com/alan2207/bulletproof-react).

**Структура папок:**

```text
src/
├── app/                 - слой приложения
│   ├── routes/          - маршруты/страницы (зависит от фреймворка)
│   ├── app.tsx          - корневой компонент
│   ├── provider.tsx     - глобальные провайдеры (QueryClient, Theme, ErrorBoundary)
│   └── router.tsx       - конфигурация роутера
├── assets/              - статика
├── components/          - общие компоненты всего приложения (UI-kit, Layout)
├── config/              - глобальный конфиг, env-переменные
├── features/            - ОСНОВНОЙ КОД: фичи
│   ├── auth/
│   ├── comments/
│   └── discussions/
│       ├── api/         - запросы и хуки запросов (useDiscussions)
│       ├── assets/      - статика фичи
│       ├── components/  - компоненты фичи
│       ├── hooks/       - хуки фичи
│       ├── stores/      - стейт фичи
│       ├── types/       - типы фичи
│       └── utils/       - утилиты фичи
├── hooks/               - общие хуки
├── lib/                 - преднастроенные библиотеки (api-client, react-query)
├── stores/              - глобальный стейт
├── testing/             - тестовые утилиты и моки
├── types/               - общие типы
└── utils/               - общие утилиты
```

Внутри фичи создаются только нужные папки, все семь не обязательны.

**Правила:**

1. **Фичи не импортируют друг друга.** Если нужно объединить `comments` и `discussions`, это делается на уровне `app` (на странице/маршруте).
2. **Однонаправленные зависимости:** `общий код (components, hooks, lib, types, utils) → features → app`. Общий код не знает о фичах, фичи не знают об `app`.
3. Правила закрепляются через ESLint `import/no-restricted-paths` (зоны `target`/`from`).
4. Импорт напрямую из файлов, а не через barrel-файлы `index.ts` (рекомендация автора ради tree-shaking в Vite).
5. **Правило продвижения (promote/demote, Robin Wieruch):** если код использует ровно одна фича, он живёт внутри неё. Как только он понадобился второй фиче, его поднимают в общие `components/`, `hooks/`, `utils/`. Бывает и обратное: «общий» код, который в итоге нужен одной фиче, опускают в неё.
6. **Тест удалением:** мысленно удалите папку фичи. Если сломалось «всё», границы протекли. Если сломались только страницы, которые её собирают, - границы в порядке.
7. Абсолютные импорты через один алиас `@/*` → `./src/*` (он не путается с пакетами из `node_modules`). Нейминг файлов и папок закрепляется линтером (`eslint-plugin-check-file`: всё в `kebab-case`).

**Масштабирование feature-based** (путь, который описывает Robin Wieruch):

```text
src/features/*                      → 5-15 фич: плоский список
src/domains/<домен>/features/*      → 20+ фич: группировка по бизнес-доменам (workspace, core, cms),
                                      домены не импортируют друг друга, общий домен - core
packages/shared                     → общий код выносится в пакет с package.json (граница пакета строже папки)
apps/* + domains/* + packages/*     → несколько приложений на одних доменах = монорепозиторий (п. 9)
```

> **Screaming Architecture** (Uncle Bob): верхний уровень структуры должен «кричать» о предметной области (`booking/`, `payments/`), а не о фреймворке (`components/`, `controllers/`). Feature-based и FSD - это реализация этой идеи. Близкая идея с бэкенда - **Vertical Slice Architecture** (Jimmy Bogard): код связывается вдоль оси изменений (фича целиком), а не по горизонтальным слоям. Минимум связей между срезами, максимум - внутри среза.

**Плюсы:** код фичи собран в одном месте, её легко найти, изменить и удалить. Простая ментальная модель: два уровня, «общее» и «фичи». Низкий порог входа по сравнению с FSD. Структура одинаково работает для Vite, Next.js, Remix и React Native.

**Минусы:** понятие «фича» не формализовано, и каждый разработчик режет по-своему. Нет отдельного места для бизнес-сущностей (`User` нужен в пяти фичах, куда его класть?). Общие папки `components/` и `utils/` со временем снова превращаются в свалку. На очень крупных проектах двух уровней иерархии не хватает.

**Когда использовать:** малые и средние SPA, команды из 1-5 человек, проекты, где FSD кажется избыточной, но структура по типам уже тесна. Хорошая промежуточная ступень перед FSD.

## 6. Feature-Sliced Design (FSD)

Формализованная **методология** структурирования фронтенд-проекта: код делится по **бизнес-смыслу и масштабу влияния**. Есть официальная спецификация, линтер и сообщество. В русскоязычном фронтенде это де-факто стандарт для средних и крупных проектов.

**Структура папок** - три уровня декомпозиции: слои → слайсы → сегменты:

```text
src/
├── app/                      СЛОЙ: инициализация приложения
│   ├── providers/            - провайдеры (store, query, theme, router)
│   ├── routes/               - конфигурация роутинга
│   ├── styles/               - глобальные стили, reset, css-переменные
│   └── index.tsx             - точка входа
│
├── pages/                    СЛОЙ: страницы
│   ├── home/                 СЛАЙС
│   └── product-details/
│       ├── ui/               СЕГМЕНТ: ProductDetailsPage.tsx
│       ├── api/              - загрузчики данных страницы (loader)
│       └── index.ts          PUBLIC API
│
├── widgets/                  СЛОЙ: крупные самостоятельные блоки UI
│   ├── header/
│   └── product-list/
│       ├── ui/
│       └── index.ts
│
├── features/                 СЛОЙ: пользовательские действия, несущие ценность
│   ├── auth-by-email/
│   ├── add-to-cart/
│   │   ├── ui/               - AddToCartButton.tsx
│   │   ├── model/            - логика, стор, селекторы
│   │   ├── api/              - мутация addToCart
│   │   └── index.ts
│   └── toggle-theme/
│
├── entities/                 СЛОЙ: бизнес-сущности
│   ├── user/
│   ├── product/
│   │   ├── ui/               - ProductCard.tsx (отображение без действий)
│   │   ├── model/            - типы Product, стор, селекторы
│   │   ├── api/              - getProduct, getProducts, маппинг DTO
│   │   ├── lib/              - formatPrice, хелперы сущности
│   │   ├── @x/               - cross-import API для других сущностей
│   │   └── index.ts
│   └── cart/
│
└── shared/                   СЛОЙ: переиспользуемый код без бизнес-логики
    ├── api/                  - api-клиент (axios/fetch инстанс), базовые типы ответов
    ├── ui/                   - UI-kit: Button, Input, Modal (можно по Atomic Design)
    ├── lib/                  - утилиты, хуки общего назначения (useDebounce, date)
    ├── config/               - env-переменные, константы, feature flags
    ├── routes/               - константы путей маршрутов
    ├── i18n/                 - настройка переводов
    └── assets/               - иконки, шрифты, изображения
```

**Слои** стандартизированы, актуальных шесть:

| Слой            | Ответственность                                                                                   | Примеры                                        | Есть слайсы?        |
| --------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------- |
| `app`           | Всё, что нужно для запуска: провайдеры, роутер, глобальные стили, инициализация                   | `providers/`, `routes/`, `styles/`             | Нет, сразу сегменты |
| ~~`processes`~~ | **Deprecated.** Раньше - сценарии на несколько страниц. Содержимое переносят в `features` и `app` | -                                              | -                   |
| `pages`         | Полноценные страницы или крупные части страниц при вложенном роутинге                             | `home`, `product-details`, `settings`          | Да                  |
| `widgets`       | Крупные самодостаточные блоки, переиспользуемые на разных страницах                               | `header`, `sidebar`, `product-list`            | Да                  |
| `features`      | Переиспользуемые **действия** пользователя, приносящие бизнес-ценность                            | `auth-by-email`, `add-to-cart`, `write-review` | Да                  |
| `entities`      | **Бизнес-сущности**, с которыми работает проект                                                   | `user`, `product`, `order`                     | Да                  |
| `shared`        | Переиспользуемый код **без бизнес-логики**, отвязанный от конкретного проекта                     | `ui`, `api`, `lib`, `config`                   | Нет, сразу сегменты |

Не все слои обязательны. Минимальный набор по спецификации - `app`, `pages`, `shared`. Остальные добавляются, когда появляется реальная необходимость. Слоя `entities` может не быть вовсе: для **тонкого клиента** (бизнес-логика на бэкенде, фронт только показывает данные) он не нужен, и это не нарушает FSD.

**Feature vs entity** (официальный FAQ): _entity_ - понятие реального мира, с которым работает приложение (существительное). _Feature_ - взаимодействие, которое приносит пользователю ценность, то, что люди хотят **делать** с сущностями (глагол).

**Слайсы** делят слой по предметной области:

- Названия слайсов **не стандартизированы**, их задаёт бизнес-домен: `user`, `cart`, `auth-by-email`.
- Фичи называются действием (глагол + объект: `add-to-cart`, `edit-profile`), сущности - существительным (`user`, `product`). Папки - в `kebab-case`.
- Слайс наружу отдаёт только **Public API** (`index.ts`).
- **Slice groups** (необязательно): когда слайсов много, связанные можно сгруппировать в папку - `entities/payment/{invoice,receipt,transaction}`, `pages/order/{create,detail,list}`. Группа - **не слайс**: у неё нет сегментов, `index.ts` и общего кода, правила изоляции между слайсами внутри группы не меняются. В `features` группировать осторожно: `features/cart/` быстро превращается в «дом для всего домена корзины» с DTO и мапперами, которые на самом деле относятся к `entities`/`shared`.

**Сегменты** делят слайс по технической роли:

| Сегмент  | Что хранит                                             |
| -------- | ------------------------------------------------------ |
| `ui`     | Компоненты, стили, форматтеры отображения              |
| `api`    | Запросы к бэкенду, маппинг DTO, хуки запросов          |
| `model`  | Модель данных: схемы, интерфейсы, сторы, бизнес-логика |
| `lib`    | Библиотечный код, нужный другим модулям этого слайса   |
| `config` | Конфигурация и feature flags                           |

Можно заводить свои сегменты, но их **называют по назначению** (`analytics`, `i18n`), а не по сути: не `components`, `hooks`, `types`. Та же логика для файлов: `types.ts`, `utils.ts`, `helpers.ts`, в которых смешаны разные домены (`DeliveryOption` + `UserInfo`), - антипаттерн **desegmentation**. Называйте файлы по домену: `delivery-price.ts`, `user-initials.ts`.

**Правила импортов:** модуль может импортировать только из **слоёв строго ниже** своего:

```text
app → pages → widgets → features → entities → shared
```

- Слайсы **одного слоя не импортируют друг друга** (cross-import). Официальная позиция: это **code smell**, а не абсолютный запрет. Такой импорт должен быть осознанным и задокументированным (стратегии решения - в corner cases ниже).
- Импорт из слайса **только через Public API**: `import { ProductCard } from '@/entities/product'`, а не `'@/entities/product/ui/ProductCard'`.
- `app` и `shared` - особые слои: у них нет слайсов, и сегменты внутри них могут импортировать друг друга.
- **`@x`-нотация для `entities`.** Если сущности реально связаны (у `Artist` есть `Song[]`), `entities/song` объявляет отдельный публичный API для конкретного потребителя: `entities/song/@x/artist.ts`, а `entities/artist` импортирует `from 'entities/song/@x/artist'`. Так связь видна явно. Документация называет `@x` **крайней мерой**: сначала проверьте, не слишком ли мелко нарезаны сущности и не стоит ли их объединить.

**Как решить, куда класть код:**

```text
Нужен для запуска всего приложения?              → app
Это целая страница / маршрут?                    → pages
Крупный блок, собирающий фичи и сущности,
используется на нескольких страницах?            → widgets
Действие пользователя с бизнес-ценностью
(глагол: добавить, оплатить, войти)?             → features
Бизнес-сущность (существительное: юзер, товар)?  → entities
Не знает о бизнесе, можно перенести в другой
проект без изменений?                            → shared
```

> **Pages first (FSD v2.1).** В v2.0 рекомендовали сразу искать в интерфейсе сущности и фичи, а страницы были тонкой композицией. В v2.1 модель обратная: **начинайте со страниц и, возможно, на них и остановитесь**. Большая часть UI и логики живёт в слайсе страницы, переиспользуемая база - в `shared`. Выносить в `widgets`/`features`/`entities` только когда код реально понадобился в нескольких местах. Слой - это глобальное пространство имён, место в нём надо расходовать экономно. v2.1 обратно совместима с v2.0.

**Corner cases FSD и официальные решения:**

| Ситуация                                                             | Решение                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Фиче нужна другая фича** (cross-import в `features`/`widgets`)     | **A.** Слайсы всегда меняются вместе → объединить в один (`profile` + `profileSettings` → `profile`). **B.** Общий доменный флоу → опустить в `entities` (только домен, без UI; напр. `entities/session` для `auth` и `profile`). **C.** Собрать на уровне выше через IoC: страница/виджет передаёт одну фичу в другую через **render props** (React), **slots** (Vue), props/context (DI). **D.** Если неизбежно - импорт только через Public API, без доступа к чужому `model`/стору |
| **Когда cross-import уже проблема**                                  | Зависимость от чужого стора/бизнес-логики, глубокие импорты во внутренние файлы, двусторонняя зависимость A↔B, изменения в одном слайсе регулярно ломают другой                                                                                                                                                                                                                                                                                                                        |
| **Сущностей слишком много** (excessive entities)                     | Не создавать слайс под каждый кусок логики. Сначала держать логику в `model` страницы/фичи. CRUD-запросы - в `shared/api`, а не в `entities`. Вместо `order` + `order-item` + `order-customer-info` с `@x` между ними - один изолированный контекст `order-info`                                                                                                                                                                                                                       |
| **Где хранить токен авторизации**                                    | Cookie - лучший вариант, архитектурных решений не требует. Иначе: **`shared/api`** (состояние в API-клиенте, refresh как middleware) или **`shared/auth`** (если логика токенов сложная). Либо **`entities/user`** (стор в `model`) + передача токена в API-клиент через контекст/подписку, провайдер в `app`. **Не хранить** в `pages`/`widgets`                                                                                                                                      |
| **Данные авторизации (токен, DTO пользователя)**                     | В `shared/auth` или `shared/api`, а не в `entities/user`: auth-ответ контекстно-специфичен, а сущность в `shared` импортировать нельзя                                                                                                                                                                                                                                                                                                                                                 |
| **Страница логина / диалог логина / 2FA**                            | Отдельная страница → `pages/login` (логин, регистрация и 2FA в одном слайсе). Диалог, открываемый на любой странице → `widgets`. Схема валидации (Zod) - в `model` страницы                                                                                                                                                                                                                                                                                                            |
| **Logout**                                                           | Запрос - рядом с кнопкой (например, `widgets/header/api`) или в `shared/api` рядом с `login`. При неудачном logout/refresh токен всё равно очищать                                                                                                                                                                                                                                                                                                                                     |
| **Куда класть запросы к API**                                        | По умолчанию `shared/api/client.ts` + `shared/api/endpoints/*.ts`. Запрос нужен одному слайсу → сегмент `api` этого слайса, в Public API не экспортировать. Не класть ответы API в `entities` преждевременно: DTO бэкенда ≠ модель фронта                                                                                                                                                                                                                                              |
| **Сгенерированный клиент (OpenAPI: orval, openapi-typescript)**      | `shared/api/openapi/` + README: что это и как перегенерировать                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **TanStack Query: ключи и query factories**                          | `queryOptions` (v5) в `shared/api/queries/*` или по контроллерам `shared/api/<controller>/<name>.query.ts`. Если запросы соответствуют сущностям → `entities/<name>/api/<name>.query.ts`. **Мутации отдельно от запросов** - часто в `api` страницы/фичи, где они вызываются                                                                                                                                                                                                           |
| **DTO и мапперы**                                                    | Рядом с функцией запроса: `shared/api/songs.ts` (DTO + `adaptSongDTO`) или `entities/song/api/{dto,mapper}.ts`. Если типы бэкенда в общем пакете - импортировать оттуда                                                                                                                                                                                                                                                                                                                |
| **Типы**                                                             | **Не создавать** `shared/types` и сегмент `types` (описывает суть, а не назначение). Utility-типы - `type-fest` или `shared/lib/utility-types` с README. Связанные типы сущностей - дженерик-параметром (`Song<ArtistType>`) или через `@x`                                                                                                                                                                                                                                            |
| **Layout страниц**                                                   | Простой (только разметка) → `shared/ui/layout` или `app/layouts`. Нужны виджеты внутри → layout в `app` (в конфиге роутера, вложенные маршруты) или передача виджетов через render props/slots. Если layout на 2-3 страницах и простой - **скопировать**: layout меняется редко, преждевременная абстракция дороже                                                                                                                                                                     |
| **URL страниц зашит в `entities`** (`href="/post/${id}"` в карточке) | Работа с URL и редиректами - на уровне `pages` и выше. Вниз ссылка передаётся через props/композицию/фабрики. Константы путей - `shared/routes`                                                                                                                                                                                                                                                                                                                                        |
| **Большой легаси-проект переходит на FSD**                           | Не переводить команду силой, даже если вы лид, - сначала договориться и получить согласие менеджмента. Пошагово: алиас `@` → `src` → разделить код по `pages` (роуты тонкие, реэкспортируют страницу) → всё, что не импортирует страницы, в `shared`, всё, что импортирует, в `app` → дальше постепенно выделять `entities`/`features`. Миграция не останавливает разработку фич                                                                                                       |

**Steiger** (`npx steiger src`) проверяет правила автоматически. Ключевые правила: `forbidden-imports`, `no-cross-imports`, `no-higher-level-imports`, `no-public-api-sidestep`, `public-api`, `no-wildcard-exports`, `insignificant-slice` (слайс используется один раз), `excessive-slicing`, `segments-by-purpose`, `no-reserved-folder-names`, `no-processes`, `ambiguous-slice-names`, `repetitive-naming`, `typo-in-layer-name`.

> **FSD + Next.js.** Next.js использует папки `app/` (App Router) и `pages/` (Pages Router), а они конфликтуют со слоями FSD. Официальная рекомендация: **переименовать слои FSD в `_app` и `_pages`** (при любом роутере). Папку `app/` Next.js удобно положить в корень проекта, а FSD - в `src/`. Файлы `page.tsx` в роутинге Next.js тогда только реэкспортируют страницу из `src/_pages/...`.

**Плюсы:** стандарт с документацией, одинаковый в разных компаниях, поэтому новый разработчик быстро ориентируется. Для любого нового кода есть предсказуемое место. Строгие правила импортов дают низкую связанность и отсутствие циклов. Границы проверяются автоматически линтером [Steiger](https://github.com/feature-sliced/steiger). Фичи и сущности легко удалить или переписать изолированно. Не привязана к фреймворку (React, Vue, Angular, Svelte).

**Минусы:** ощутимая кривая обучения, вечные споры «это feature или entity», «widget или feature». Заметный оверхед на маленьких проектах и MVP. Много мелких папок и файлов `index.ts`. Жёсткая слоистость иногда избыточна для простых CRUD-экранов. Нужны договорённости по `@x` и кросс-импортам сущностей. Стейт-менеджер методология не выбирает, это отдельное решение.

**Когда использовать:** средние и крупные SPA/SSR-приложения, несколько разработчиков или команд, долгоживущие продукты с ожидаемым ростом функциональности.

## 7. Atomic Design

Методология Brad Frost (2016) для структурирования **только UI-компонентов** дизайн-системы. Бизнес-логику, API и стейт она не затрагивает, поэтому применяется не ко всему проекту, а к UI-kit внутри него.

**Структура папок:**

```text
shared/ui/                 (или отдельный пакет packages/ui в монорепозитории)
├── atoms/          - неделимые элементы: Button, Input, Label, Icon
├── molecules/      - группы атомов с одной функцией: SearchField = Input + Button
├── organisms/      - сложные секции: Header, ProductGrid, LoginForm (только UI)
├── templates/      - каркасы страниц с плейсхолдерами
└── pages/          - шаблон с реальными данными (обычно в проекте не выделяют)
```

**Правила:** компонент уровня N собирается только из компонентов уровней ниже N (atom не импортирует molecule).

**Плюсы:** визуальная консистентность и переиспользуемость. Общий язык с дизайнерами: компоненты в Figma и в коде совпадают. Отлично ложится на Storybook.

**Минусы:** не отвечает на вопрос, где бизнес-логика, стейт и API. Граница molecule/organism субъективна и вызывает споры. Уровни `templates`/`pages` конфликтуют с роутингом и слоями проекта, поэтому в реальных проектах используют только 3 нижних уровня.

**Когда использовать:** собственный UI-kit или дизайн-система. На практике - внутри `shared/ui` в FSD, `components/` в feature-based или отдельным пакетом `packages/ui` в монорепозитории.

## 8. Clean Architecture / Hexagonal (Ports & Adapters)

Clean Architecture Robert C. Martin (2012) и Hexagonal Alistair Cockburn (2005) переносят на фронтенд **Dependency Rule**: зависимости направлены **только внутрь**, к бизнес-логике. Домен ничего не знает о React, роутере, HTTP-клиенте и браузере.

**Структура папок:**

```text
src/
├── domain/                  ЯДРО: не импортирует ничего снаружи
│   ├── entities/            - сущности и бизнес-правила: Order.ts, Money.ts
│   └── value-objects/
├── application/             СЦЕНАРИИ: знает только domain
│   ├── use-cases/           - checkout.ts, applyDiscount.ts
│   └── ports/               - интерфейсы: OrderRepository, PaymentGateway, Notifier
├── infrastructure/          АДАПТЕРЫ: реализуют порты
│   ├── api/                 - RestOrderRepository (fetch/axios)
│   ├── storage/             - LocalStorageCartRepository
│   └── di/                  - сборка зависимостей (composition root)
└── presentation/            UI: React-компоненты, хуки, стор, роутер
    ├── pages/
    ├── components/
    └── hooks/               - useCheckout() вызывает use-case с внедрёнными адаптерами
```

**Правила:**

```text
presentation → application → domain
infrastructure → application (реализует ports) → domain
```

**Ports** - интерфейсы, которые объявляет ядро (`OrderRepository`). **Adapters** - их реализации (`RestOrderRepository`, мок для тестов). Замена REST на GraphQL или React на другой UI не затрагивает `domain` и `application`. Часто Clean Architecture применяют не ко всему проекту, а внутри крупной фичи или сегмента `model` в FSD.

**Плюсы:** бизнес-логика независима от фреймворка и переживает смену React/Vue. Домен тестируется чистыми unit-тестами без DOM и моков сети. Направление зависимостей исключает спагетти-импорты. Одну логику можно переиспользовать в web, mobile и desktop.

**Минусы:** большой оверхед абстракций для типичного фронтенда, где «логика» - это получить JSON и показать. Много файлов, интерфейсов и DI ради самой структуры. Плохо стыкуется с идиомами React (хуки, Server Components, TanStack Query уже решают часть задач). Без дисциплины слои быстро «протекают». Высокий порог входа.

**Когда использовать:** приложения со сложной клиентской бизнес-логикой (финтех-калькуляторы, редакторы, offline-first, торговые терминалы), общий домен для нескольких платформ, долгоживущие продукты, где фреймворк вероятно сменится.

## 9. Монорепозиторий (Nx, Turborepo, pnpm workspaces)

Способ организовать **несколько приложений и общих библиотек** в одном репозитории. Это уровень выше `src/`: внутри каждого приложения всё равно применяется FSD или feature-based.

**Структура папок:**

```text
repo/
├── apps/                    - развёртываемые приложения
│   ├── web/                 - основной сайт (внутри - FSD)
│   ├── admin/               - админка
│   └── mobile/              - React Native
├── packages/                - общие библиотеки
│   ├── ui/                  - дизайн-система (Atomic Design + Storybook)
│   ├── api-client/          - сгенерированный клиент API (OpenAPI)
│   ├── utils/               - общие утилиты
│   ├── eslint-config/       - общие правила линтинга
│   └── tsconfig/            - базовые tsconfig
├── package.json             - workspaces
├── pnpm-workspace.yaml
└── turbo.json / nx.json     - граф задач, кеширование сборок
```

**Правила:**

- `apps` зависят от `packages`, но никогда наоборот. `apps` не импортируют друг друга.
- В Nx библиотеки размечают тегами (`type:feature`, `type:ui`, `type:data-access`, `type:util`, `scope:admin`), а правило `@nx/enforce-module-boundaries` запрещает недопустимые зависимости, например `ui → feature`.
- Кеширование и запуск задач только для изменённых пакетов (`affected`).

**Плюсы:** единые версии зависимостей и конфигов. Переиспользование кода между приложениями без публикации в npm. Атомарные изменения во всех приложениях одним PR. Быстрые сборки и CI за счёт кеширования.

**Минусы:** сложнее настройка CI и тулинга, большой репозиторий, нужна дисциплина версионирования общих пакетов, изменение в `packages/ui` затрагивает все приложения.

**Когда использовать:** в компании несколько фронтенд-приложений (сайт, админка, мобильное) с общим UI-kit и API-клиентом.

## 10. Микрофронтенды (Micro-frontends)

Разбиение большого фронтенда на **независимо разрабатываемые и деплоящиеся приложения**, за каждым из которых закреплена своя команда. Итоговый интерфейс собирается во время выполнения. Это организационная архитектура, перенесённая с микросервисов.

**Структура:**

```text
shell/ (host)                 - оболочка: роутинг верхнего уровня, авторизация, layout
├── remotes: catalog, checkout, profile
catalog/  (remote, команда A) - свой репозиторий/пакет, свой деплой, внутри FSD
checkout/ (remote, команда B)
profile/  (remote, команда C)
shared/                       - дизайн-система и контракты событий (часто в монорепо)
```

**Способы композиции:**

| Подход                                                     | Суть                                                                        | Особенности                                                                                  |
| ---------------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Build-time (npm-пакеты)                                    | Части собираются в общий бандл на этапе сборки                              | Просто, но релизы всех частей связаны, так что это не «настоящие» микрофронтенды             |
| iframe                                                     | Каждая часть - отдельный документ                                           | Максимальная изоляция, но сложны роутинг, авторизация, адаптивность, SEO                     |
| single-spa                                                 | Оркестратор монтирует приложения по маршруту                                | Не зависит от фреймворка, зрелая экосистема                                                  |
| Module Federation (Webpack 5, Rspack, Vite-плагин, MF 2.0) | Приложения отдают и потребляют модули в рантайме, общие зависимости шарятся | Сейчас самый популярный вариант, но нужна синхронизация версий `shared`-зависимостей (React) |
| Web Components                                             | Каждая часть - custom element                                               | Композиция на уровне браузерного API, независимо от фреймворка                               |

**Правила:** микрофронтенды не импортируют код друг друга, общаются только через контракты (custom events, URL, общий event bus, props от shell). Общее ограничивают дизайн-системой и минимальным shared-слоем. Каждая часть владеет своим бизнес-доменом (вертикальная нарезка по домену, а не по UI-блокам).

**Плюсы:** независимые релизы команд. Разные стеки или версии фреймворка в разных частях. Организационное масштабирование (закон Конвея). Сбой одной части не обязательно ломает всё приложение. Постепенная миграция легаси (strangler pattern).

**Минусы:** высокая операционная сложность (оркестрация, версионирование, CI/CD на каждую часть). Риск дублирования зависимостей и раздувания бандла. Трудно сохранить единый UX и дизайн. Сквозные сценарии сложно отлаживать и тестировать.

**Когда использовать:** крупные организации с несколькими независимыми фронтенд-командами, которым нужен раздельный релизный цикл, или миграция большого легаси по частям. **Для одной команды не рекомендуется**: сложность не окупается.

| ------------------------- | --------------- | ------------------------- | --------------------------------------- | ------------------------------------------------ | ------------------------------------------------ |
| MVC                       | Низкий          | Малый                     | Простое разделение данных и отображения | Разрастание Controller, каскадные обновления     | SSR-фреймворки, небольшие приложения             |

| MVVM                      | Средний         | Любой                     | Декларативный binding UI и состояния    | Скрытый граф реактивных связей                   | Angular, Vue, формоёмкий UI                      |

| Feature-based             | Низкий          | Малый-средний             | Код фичи в одном месте                  | «Фича» не формализована, нет места для сущностей | Малые/средние SPA, 1-5 разработчиков             |

| Atomic Design             | Низкий          | Любой                     | Консистентный UI-kit                    | Не решает бизнес-логику                          | Дизайн-системы, `shared/ui`                      |
| Clean / Hexagonal         | Высокий         | Любой, со сложной логикой | Домен независим от фреймворка           | Много абстракций для CRUD                        | Сложная клиентская логика, мультиплатформенность |
| Монорепозиторий           | Средний         | Несколько приложений      | Общий код без публикации                | Сложный тулинг и CI                              | Несколько приложений с общим UI/API              |
| Микрофронтенды            | Высокий         | Очень крупный             | Независимые релизы команд               | Операционная сложность                           | Много независимых команд                         |

> **Архитектуры не взаимоисключающие, а комбинируются.** Типичный стек крупного продукта: монорепозиторий (Turborepo/Nx) → в каждом приложении FSD → внутри слайсов роли MVVM (`ui` = View, `model` = ViewModel/Model) → `shared/ui` или `packages/ui` по Atomic Design → в сложных доменах Clean Architecture. Микрофронтенды добавляются, только если нужны независимые релизы команд.

## Как выбрать архитектуру

```text
Прототип / лендинг / 1 разработчик          → по типам файлов
Небольшое SPA, 1-5 разработчиков            → Feature-based (Bulletproof React)
Средний/крупный продукт, растущая команда   → Feature-Sliced Design
Angular / Vue                               → + MVVM внутри модулей (встроен во фреймворк)
Серверный рендеринг шаблонов                → MVC (Rails, Django, Laravel)
Императивный UI, критична тестируемость     → MVP
Сложная доменная логика на клиенте          → + Clean Architecture в доменных модулях
Собственная дизайн-система                  → + Atomic Design в UI-kit
Несколько приложений с общим кодом          → + Монорепозиторий (Turborepo / Nx)
Много независимых команд, раздельные релизы → + Микрофронтенды (Module Federation)
```

Проект обычно развивается постепенно: **по типам → feature-based → FSD**. Feature-based естественно перерастает в FSD: `features/` делится на `features`/`entities`/`widgets`, а `components/`, `utils/`, `hooks/` уходят в `shared/`.

## Лидеры: на что обратить внимание в первую очередь

1. **Feature-Sliced Design** - основной лидер. Это единственная полностью формализованная методология с официальной спецификацией, линтером (Steiger) и примерами для React, Vue, Angular и Next.js. Де-факто стандарт в русскоязычном фронтенд-сообществе, чаще всего встречается в вакансиях и на собеседованиях. **Рекомендуется как основная архитектура для средних и крупных проектов.**
2. **Feature-based (Bulletproof React)** - лидер для небольших и средних проектов и самый популярный подход в англоязычном React-сообществе. Проще FSD, сохраняет главное (код по фичам, запрет кросс-импортов, однонаправленные зависимости), легко мигрирует в FSD.
3. **MVVM** - стандарт в Angular и Vue. Его надо понимать, чтобы грамотно разделять шаблон (View) и логику экрана (компонент/composable как ViewModel) внутри любой из структур выше. MVC и MVP важны как основа: из их проблем выросли MVVM и современные подходы, но в новых SPA напрямую почти не применяются.
4. **Монорепозиторий + Module Federation** - лидеры для масштабирования на уровне нескольких приложений и команд. Turborepo/Nx - стандарт для монорепозиториев, Module Federation - стандарт для runtime-композиции микрофронтендов.

> **Общие для всех лидеров практики:** Public API модулей, однонаправленные зависимости, запрет импортов между модулями одного уровня, хранение связанного кода рядом (colocation), автоматическая проверка границ линтером.
